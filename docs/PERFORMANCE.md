# 性能基线与优化记录

## 2026-08-18 — SessionDB 启动路径 N+1 修复

**问题**：`SessionDB.loadAll()` 对每个会话行额外发起一次事件查询（N+1），且启动时全量解码所有会话的全部事件。会话数增长后启动时间与内存随之线性恶化。

**修复**（提交 8064f1a）：
- `loadSessions()`：仅元数据，单条 SQL，启动侧边栏专用
- `load(_ id:)`：单会话含事件，按需加载（切换会话 / 选中首个会话）
- App 层切换选中统一走 `presentSession`：先取事件再切换，`selectedSession` 永不指向空事件记录，防止 persist 按 messages 重建时误清空 DB

**回归测试**：`SessionDBTests.testLoadSessionsFastOnLargeDataset` — 300 会话 × 80 事件，元数据加载 < 1s。

## MemProbe 基线（debug 构建，M5 Mac，macOS 27）

命令：`swift run MemProbe 300`

每次迭代 = 1 次会话保存 + `loadSessions` + `load`（选中会话）+ 每 20 次删除最旧会话（与 App 启动/切换路径同款调用）。

| 日期 | 迭代数 | 耗时 | 单次 |
|------|--------|------|------|
| 2026-08-18 | 300 | 1.06s | ≈3.5ms |

### 修复前后对比（实测，2026-08-18，debug 构建，M5 Mac）

数据集：300 会话 × 120 事件（36,000 事件，事件含 3 个 text 块模拟真实负载）

| 路径 | 耗时 | 说明 |
|------|------|------|
| `loadAll()` 全量（旧启动路径） | 0.287s | N+1 事件查询 + 全量 JSON 解码 |
| `loadSessions()` 元数据（新启动路径） | 0.001s | 单条 SQL，无事件解码 |

## 2026-09-06 — 终端执行改投独立线程的开销与收益（D-17，before/after 实测）

**背景**：D-17 把 `TerminalRunner.run` 的阻塞体（50ms 轮询 + `waitUntilExit()` + `group.wait()`）
从调用方的 Swift 协作线程池改投 `Thread.detachNewThread`。改动的固有风险是
「每条命令多创建一条线程 ⇒ 短命令变慢」，故必须量化，不能只讲道理（铁律 6）。

**实测（本机 M 系 / macOS 27 beta / debug 构建 / 全 A 层零前台，同机同会话交替跑）**

| 场景 | 原版（阻塞体占协作线程） | 改后（独立线程） | 判读 |
|---|---|---|---|
| 串行 24 × `printf ok`，单条平均 | 128.048 ms | 128.387 ms | **+0.34 ms（≈0.3%）＝线程创建成本，落在噪声内** |
| 串行 24 条 min / max | 119.004 / 133.280 ms | 124.161 / 133.319 ms | 分布形态未变 |
| 并发 24 × `sleep 0.05` 墙钟 | **537 ms** | **185 ms** | **≈2.9× 提速**：原版 24 条命令把协作线程占死⇒排成串行，改后真并行 |
| 并发 24 条成功率 | 24/24 | 24/24 | 换线程未改变执行语义 |

**结论（两句）**：① 单命令开销可忽略（0.34ms，相对 zsh 启动本身 ~128ms 无意义），
「每条命令新建线程」的代价无需引入线程池；② 收益在并发面（2.9×），这正是母 Agent
并行派发子任务／多会话同时跑命令的场景，与 D-17 立项理由一致。

**单条 128ms 的构成（顺带测得，登记为已知成本，未处理）**：一次终端执行的地板价 ≈128ms，
由 `/bin/zsh` fork+exec 与 **50ms 轮询粒度**共同决定（`pollUntilExit` 只在 `Thread.sleep(0.05)`
边界上发现进程已退出）。命令越短，被轮询粒度垫高的比例越大 ⇒ 若要压延迟，
应改事件驱动（`terminationHandler`，见 D-17 (b) 案）或缩短轮询间隔，而非改线程模型。
